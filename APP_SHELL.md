# Prism — оболочка приложения (меню, экраны, комнаты): дизайн

> Каркас всего приложения вокруг матча: главное меню, навигация, экраны, и
> сетевая стыковка через **комнаты по коду с паролем**. Без аккаунтов и без имён
> игроков. Это источник правды по «оболочке»; реализуется по фазам (раздел 8).
> Решения пользователя (зафиксированы): **идентичности/имён НЕТ**; матчмейкинг —
> **коды комнат, пароль обязателен при создании**; сначала этот док, потом код.

## 0. Где мы сейчас (исходная точка)

- Клиент — **один экран**: строка `ws://...` + кнопка «Подключиться» → сразу борд
  (`Main.gd`, после рефактора — координатор матча + 9 модулей).
- Сервер — **один матч на процесс**: первые 2 подключения по WebSocket попадают в одну
  партию (`server/src/main.cpp`), при дисконнекте процесс завершает матч.
- Нет: меню, навигации, экранов, комнат, идентичности.

## 1. Принципы оболочки

1. **Без аккаунтов и имён.** Игрок — анонимный слот. В матче стороны — «ВЫ / СОПЕРНИК»
   (как сейчас). Никаких профилей, ников, регистрации, БД.
2. **Приватность — через комнату.** Стыковка двух игроков: **код комнаты** (какая партия)
   + **пароль** (доступ). Пароль обязателен при создании. Это не «безопасность аккаунта»,
   а простой общий секрет для приватного матча на общем сервере.
3. **Роутер экранов.** Корневой узел переключает экраны; матч (нынешний `Main.gd`) — один из
   экранов. Меню/настройки/лобби — отдельные лёгкие экраны. Стыкуется с рефактором.
4. **Стиль — наш** (свет на тьме, как борд): меню/кнопки в той же палитре и атмосфере, не
   дефолтный Godot-вид.
5. **Без эмодзи** в UI (правило проекта) — только текст и SVG-иконки.

## 2. Карта экранов (стейт-машина роутера)

```
[Запуск]
   │
   ▼
[Главное меню] ─► Играть ─► [Меню игры] ─┬─ Создать комнату ─► [Ожидание] ─► [Матч] ─► [Результат] ─► в меню
   │                                      ├─ Войти по коду ───►            ↗
   │                                      └─ Поиск (заглушка) ─► (позже: автоматчмейкинг)
   ├─► Настройки   (адрес сервера, звук — БЕЗ имени)
   ├─► Колоды      (заглушка сейчас; позже — выбор/сборка)
   └─► Выход
```

Экраны (каждый — отдельный `class_name`-узел под роутером):
- **MainMenu** — заголовок игры + кнопки.
- **PlayMenu** — «Создать комнату» / «Войти по коду» / «Поиск» (заглушка) (+ назад).
- **CreateRoom** — поле пароля (обязательно) → «Создать».
- **JoinRoom** — поля код + пароль → «Войти».
- **RoomWait** — показывает код комнаты, «ожидание соперника…», «отмена».
- **Match** — нынешний борд (`Main.gd`).
- **Result** — победа/поражение (уже есть как оверлей) → «В меню» / «Реванш».
- **Settings** — адрес сервера, громкость (позже). Имени НЕТ.

## 3. Главное меню — кнопки (точно)

- **Играть** → PlayMenu. Главная кнопка, крупная, в центре.
- **Колоды** → заглушка «скоро» (или скрыта до дека-модели).
- **Настройки** → Settings.
- **Выход** → закрыть приложение.
- Шапка: название «PRISM» + подзаголовок-флавор. Профиля/ника НЕТ (идентичности нет).

## 4. Поток «Играть» (комнаты по коду + пароль)

В PlayMenu три варианта: **Создать комнату**, **Войти по коду**, и **Поиск** (заглушка).

**Поиск (заглушка сейчас):** кнопка-плейсхолдер под будущий **автоматчмейкинг** — сервер сам
сводит двух ждущих игроков без кода/пароля (публичная очередь). Пока: кнопка есть, но
неактивна/«скоро» (не шлёт ничего). Реализуется пост-MVP (нужна очередь на сервере + позже ранги).

**Создание (хост):**
1. PlayMenu → «Создать комнату» → CreateRoom.
2. Игрок вводит **пароль** (обязателен; пустой не принимается).
3. Клиент шлёт серверу `createRoom{password}`.
4. Сервер создаёт комнату, **генерирует короткий код** (например 4 символа A–Z/2–9, без
   неоднозначных 0/O/1/I), кладёт хост в слот 1 → отвечает `roomCreated{code}`.
5. RoomWait показывает **код** (его игрок передаёт другу любым способом) + «ожидание соперника».

**Вход (гость):**
1. PlayMenu → «Войти по коду» → JoinRoom.
2. Игрок вводит **код + пароль** → клиент шлёт `joinRoom{code, password}`.
3. Сервер валидирует: комната существует? пароль совпадает? есть свободный слот?
   - ошибка → `joinError{reason}` (нет комнаты / неверный пароль / комната занята) → текст на экране.
   - ок → гость в слот 2.
4. Когда в комнате **2 игрока** — сервер создаёт `Game` и шлёт обоим `matchStart` + первый `view`
   → оба клиента переходят на экран Match.

**Связь и адрес сервера.** Клиент всё равно держит **адрес сервера** (Settings; дефолт — будущий
хостед-адрес). Код+пароль — это «какая комната внутри сервера», а не «где сервер». Реальность:
- **Ngrok/локально:** друг получает **адрес сервера (URL) + код + пароль**. (Код+пароль — слой
  поверх общего URL; на одном сервере может быть несколько комнат.)
- **Фиксированный VPS (пост-MVP):** URL зашит в клиент → друг получает **только код + пароль**.
  Вот тут коды раскрывают весь смысл (делиться нечем, кроме кода). Это аргумент за хостинг позже.

**Решено: пока ngrok/локально** (хостинг на VPS — пост-MVP). То есть на этом этапе друг получает
**адрес сервера + код + пароль**; адрес вводится в Settings/JoinRoom. Коды комнат всё равно нужны
(на одном сервере несколько комнат), но полный их смысл («делиться только кодом») раскроется после
хостинга.

## 4a. Колода в потоке (по режиму) — на будущее

Между «комната заполнена» и «матч стартовал» логически есть **шаг выбора колоды** — но он
**зависит от режима** и НЕ всегда показывается:
- **Режимы с выбором** (свободная игра, ранг): игрок выбирает колоду перед матчем (экран
  DeckSelect; стыкуется с дека-моделью). Оба выбрали → старт.
- **Режимы без выбора** (арена/драфт, «дуэль на заданных», обучение): колоду **выдаёт** сервер
  (фиксированную/сгенерированную); экрана выбора нет — сразу матч.

**СДЕЛАНО — лоадаут после «Играть» (решение пользователя).** Выбор героя+колоды вынесен в **экран
`LoadoutSelect` сразу после «Играть»**, до комнат (НЕ синхронный шаг в начале матча — выбор
локальный, едет с `createRoom`/`joinRoom`). Поток:
`Меню → Играть → LoadoutSelect (герой ◀ | колода ▶) → Создать/Войти комнату → Ожидание → Матч`.
- Слева — 4 героя (портрет + пассив), выбрать одного. Справа — **список колод игрока** (модель
  «коллекции»: может быть пустым → бой нельзя начать; сейчас одна `Decks.standard()` = весь
  не-геройский пул, выводится из `CardData`). «Далее» активна только если выбраны герой И колода.
- Выбор сохраняется в `user://settings.cfg` (`[loadout] hero/deck`), восстанавливается.
- Протокол: `createRoom`/`joinRoom` несут `hero` (id) и `deck` (список card_id). Сервер (`Room.hero[2]`/
  `deck[2]`, `readLoadout`, `startMatch`) сажает игрока с его лоадаутом; фолбэк — рандом-герой +
  `demoDeck` (старый клиент / пустой выбор). Стандартная колода == старый `demoDeck`, геймплей не
  меняется.
- Назад: LoadoutSelect→меню (дропает сокет, если открыт), PlayMenu-назад→LoadoutSelect (переподбор).
- **Дека-модель/билдер** (лимиты копий, кривая, пользовательские колоды, экран коллекции) — позже,
  когда вырастет пул; `Decks.all()` уже моделирует список колод игрока (см. `BACKLOG`).

## 5. Серверная модель комнат (рефактор `main.cpp`)

Сейчас сервер = «один глобальный матч». Нужно перейти к **менеджеру комнат**:

- **Room** = `{ code, password, fd[2] (сокеты игроков), Game* (создаётся при заполнении), state }`.
  state: `Waiting` (1 игрок) → `Playing` (2 игрока, Game идёт) → закрытие.
- **Лобби-протокол** (до попадания в матч): подключившийся сокет сперва в «лобби»-состоянии,
  шлёт `createRoom`/`joinRoom`; сервер отвечает `roomCreated`/`joinError`/`matchStart`.
  Игровые действия (`play/attack/...`) принимаются только в `Playing`.
- **Матч в комнате** = существующая логика `Game` + `viewJson`/`applyAction`, просто привязанная
  к конкретной комнате, а не к глобалу.
- **Жизненный цикл / дисконнекты:**
  - в `Waiting` отвалился хост → комната удаляется; гость (если успел) → ошибка/назад в меню.
  - в `Playing` отвалился любой → матч завершается (как сейчас), второму — `opponentLeft` →
    экран Result/меню. Комната чистится.
  - пустые/протухшие комнаты удаляются (TTL, чтобы не копились).
- **Пароль:** хранится в памяти комнаты (комнаты эфемерны). Не хеш — для хобби-проекта ок;
  транспорт — `wss` (TLS), так что пароль не идёт открытым по сети. Это **не** «безопасность
  аккаунтов», а замок на приватную комнату.
- **Один процесс — много комнат.** Accept-цикл больше не «взять 2 и играть», а «принимать
  сокеты, вести их через лобби, матчить по комнатам». Это средняя по объёму, но локальная правка.

## 6. Протокол — добавки (лобби-фаза)

Клиент → сервер:
- `{action:"createRoom", password:"..."}`
- `{action:"joinRoom", code:"ABCD", password:"..."}`
- `{action:"leaveRoom"}` (отмена ожидания / выход в меню)

Сервер → клиент:
- `{type:"roomCreated", code:"ABCD"}`
- `{type:"joinError", reason:"no_room|bad_password|room_full"}`
- `{type:"matchStart"}` (далее идут обычные `view`-сообщения матча)
- `{type:"opponentLeft"}` (соперник вышел в матче/ожидании)

Существующие игровые сообщения (`view`, действия) — без изменений, но обрабатываются в контексте
комнаты. (Текущий `view` — без обёртки `type`; добавить либо поле `type:"view"`, либо различать по
наличию ключей. Решить при реализации; не ломать клиентский `_ingest_view`.)

## 7. Как ложится на архитектуру

- **Клиент:**
  - Новый корневой **`Router`** (Control), переключает экраны (`add/remove child` или `visible`).
  - `Net` (уже есть) делаем **persistent** на уровне роутера, а не матча: лобби-сообщения и
    матч-сообщения роутятся по текущему экрану/состоянию.
  - Нынешний `Main.gd` становится экраном **Match** (его connect-бар убираем — подключение теперь
    в лобби-флоу).
  - Новые лёгкие экраны: `MainMenu`, `PlayMenu`, `CreateRoom`, `JoinRoom`, `RoomWait`, `Settings`.
    Кнопки/панели — через существующие `Ui`/`Tokens`/`Chrome`-фабрики (единый стиль).
- **Сервер:** `RoomManager` + лобби-состояние сокета; `Game` переезжает «внутрь комнаты».
  Тесты движка не затрагиваются (логика `Game` та же).

## 8. Фазы реализации (порядок — снизу вверх, безопасно)

1. **Фаза A — скелет оболочки (клиент, без изменений сервера). [СДЕЛАНО]** Router (`router.gd`,
   корень `App.tscn`) + MainMenu (`main_menu.gd`) + Settings (`settings_screen.gd`) + Match
   (`Main.gd`) под роутером + Result→меню. Общий фон вынесен в `backdrop.gd`. Кнопка «Играть» пока
   ведёт в **прямой connect** к адресу из Settings (нынешний флоу). Адрес хранится в
   `user://settings.cfg`. Выход из матча — сигнал `exit_to_menu` (кнопка «В меню» + game-over).
   Проверено скриншотами (`ShotMenu.gd`) и парсом проекта.
2. **Фаза B — комнаты (сервер + клиент). [СДЕЛАНО]** Сервер переписан в event-loop менеджер комнат
   (`server/src/main.cpp`): сокеты ведутся через лобби, `createRoom`/`joinRoom`/`leaveRoom` +
   пароль, серверные коды (4 символа, без `0/O/1/I`), `roomCreated`/`joinError`/`matchStart`/
   `opponentLeft`, много комнат на процесс. Клиент: `Router` стал сетевым хабом (владеет `Net`,
   роутит лобби-ответы vs. view), экраны `PlayMenu`/`CreateRoom`/`JoinRoom`/`RoomWait`; `Main` —
   экран матча через инъекцию (`bind(sender)`/`feed_view`), кнопка «В меню» на всегда-верхнем слое
   (кликабельна и в мулигане). Переподключение после рестарта сервера (мёртвый `Net`
   освобождается, отправка переустанавливает связь). Проверено: 10 edge-кейсов сервера + e2e
   (создать→войти→матч), reconnect, server-restart, connection-refused.
3. **Фаза C — выбор перед матчем.** Герой/колода до старта (стыкуется с дека-моделью).
4. **Пост-MVP.** Хостинг на VPS (фиксированный URL → делиться только кодом), звук, ранги/коллекция,
   и при желании — аккаунты (если понадобятся прогрессия/рейтинг).

## 9. Открытые вопросы (решить при реализации, не сейчас)

- Реванш в Result — новая комната с тем же кодом/паролем, или просто «в меню»? (План: «в меню» в
  Фазе A; реванш — позже.)
- Несколько матчей на одном сервере одновременно — поддерживаем (модель комнат это уже даёт).
- `type`-обёртка для всех сообщений vs различение по ключам (см. раздел 6).
