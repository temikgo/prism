### Остановка дробления — осознанное решение (не «не успел»)

Оставшиеся builder-ы (`_board_row`/`_creature_card`, `_hand_row`, `_manarow_view`/`_awaken_chip`/
`_revealed_thumb`, `_aura_tile`, overlays Mulligan/Scry/GameOver) — **уже не самостоятельные
виджеты, а view-контроллеры, сросшиеся с координатором**: держат состояние в Main (`_mull_sel`,
`_scry_sel`, `_card_nodes`) и зовут его методы из closures (`_attack_creature`/`_play_at_drop`/
`_can_play_here`/`_rebuild`/`_make_card`/`_ability_*`). Чтобы вынести — нужна host-инъекция и вызовы
`host._method(...)`, которые **парсер не проверяет** (только живой тест), при малом выигрыше и
реальном риске. **Решение: дальнейшее механическое дробление НЕ делаем.** Настоящий следующий шаг
для этой части — архитектурный: **инкрементальный апдейт борда вместо полного `_rebuild`** (см.
раздел 5). Тогда у виджетов появится явная модель узлов и сигнальная шина, и разнос станет
естественным и безопасным. До тех пор board/hand/overlay-сборка legitimately живёт в координаторе.

**Итог:** `Main.gd` 2415 → ~1480 строк (−39%); **9 модулей** (CardData, Tokens, Fx, Net, GameState,
CardView, HeroView, Chrome, ManaPicker). Вынесено всё, что выносится чисто: чистая логика, визуал
карты/героя, board-chrome, сервисы (сеть/состояние/анимации), самодостаточный оверлей-пикер. Дубли
builder-ов убраны. Поведение не менялось (делегаты + чистые переносы; парс+скрин после каждого
шага). Остаток Main — координатор + сросшаяся интерактивная сборка борда (разносить — с архзадачей).



> Principal-level ревью клиента (`client-godot/`) и поэтапный план. Цель — разбить
> god-object `Main.gd` на модули с тестируемыми швами, убрать дублирование, не меняя
> поведение. Каждая фаза самодостаточна, проверяется скриншот-стендом `Shot.gd` + ручным
> прогоном, и коммитится отдельно. **Поведение при извлечении не меняем** (чистые переносы).

## 1. Диагноз

`Main.gd` — **2415 строк, ~100 функций, 5+ ответственностей в одном файле**:
транспорт (WebSocket), диффинг состояния, анимации/FX, правила/запросы к состоянию,
и вся сборка виджетов. Это классический **god-object** без слоёв.

Метрики (факты из кода):
- **43 функции** напрямую читают глобалы `view` / `cards` → нет шва для тестов и переиспользования.
- **30** `add_theme_stylebox_override`, **14** `StyleBoxFlat.new()`, **41** `Ui.label`,
  **65** инлайновых `mouse_filter = IGNORE`, **8** `Panel.new()`, **6** `TextureRect.new()` —
  много повторяемого бойлерплейта сборки UI.
- Клиентских тестов **0** (в движке — 70).

## 2. Конкретные запахи (с доказательствами)

1. **God-object / нарушение SRP.** Один файл делает сеть, состояние, анимации, правила и весь UI.
   Любая правка трогает гигантский файл; диффы/мерджи болезненны.
2. **Дублирование builder-ов:**
   - `_gem` (l.2102) ≈ `_stat_gem` (l.1061) — две почти идентичные реализации круглого бейджа
     (различие лишь в размере/альфе). Должна быть одна параметризованная.
   - `_art_thumb` (l.1229) ≈ `_art_full` (l.2120) — два загрузчика арта (thumbnail vs full),
     общая логика «есть png → TextureRect, иначе плейсхолдер».
   - Стиль-фабрики размазаны: `_round_style` (Main), `Ui.bordered`, `Ui.glass`, инлайновые
     StyleBox в `_gem`/`_stat_gem`/`_cost_badge`/`_aura_tile`/… — нет единой точки.
3. **Primitive obsession / stringly-typed.** Карты и существа — везде `Dictionary`
   (`d.get("cost", {})`, `cr.get("atk", 0)`, `slot.get("color","colorless")`); payload-ы драга —
   нетипизированные словари; цвета/ключевики/типы — голые строки. Нет типизированной модели →
   опечатки в ключах ловятся только в рантайме.
4. **Скрытая связность.** Builder-функции читают глобалы `view`/`cards` вместо параметров →
   нельзя ни протестировать, ни переиспользовать изолированно. `UiCard` хранит глобальное
   изменяемое состояние в статиках (`active_drag`, `aim_from`, `aim_color`).
5. **Магические числа/цвета.** Десятки `Color(...)`-литералов и размеров разбросаны по коду —
   нет таблицы дизайн-токенов (палитра/типошкала/радиусы/тени).
6. **Полный ребилд на каждый `view`** (`_rebuild` сносит и пересобирает всё дерево). Работает,
   но: (а) дороже, (б) усложняет межсостоянные анимации (карта рука→стол). Это **архитектурная**
   задача, не косметика — выносим в отдельный пункт, **не** трогаем в рамках модуляризации.
7. **Нет клиентских тестов** → рефакторить «вслепую». Шов из п.1–4 это и чинит (появится что тестировать).

## 3. Целевая архитектура

```
Main (координатор, ~150–250 строк)
 ├─ Net            — WebSocket: connect/poll/send/recv → сигналы (state_received)
 ├─ GameState      — хранит view; диффит входящие → сигналы damaged/died/summoned
 ├─ BoardView      — строит дерево из данных; emit-ит намерения (attack/play/place_mana/awaken)
 │    ├─ CardView (UiCard+лицо+тултип+статусы)   ├─ HeroMedallion   ├─ PilesColumn
 │    ├─ ManaRow/AwakenChip                       ├─ BoardRow        ├─ HandRow
 │    └─ overlays: Mulligan / Scry / GameOver / ColorPicker
 ├─ Fx             — lunge/shake/pop-in/float-numbers/motes (+ FxLayer)
 └─ модули-данные (без зависимостей от UI):
      CardData     — lookup/cost/name/keywords/target-side/affordability (чистые функции)
      Tokens/Theme — дизайн-токены + фабрики (gem/chip/label/style/art) — единая точка
```

Принцип: **данные вниз, сигналы вверх.** View-узлы принимают plain-данные и **emit-ят намерения**
(`attack_requested(attacker,target)`), а не дёргают `_send` напрямую. `Main` — единственный, кто
знает про сеть и склеивает всё.

## 4. План по фазам (снизу вверх — безопасно)

Извлекаем сначала листовую чистую логику (наименьший риск), потом виджеты, потом сервисы.

- **Фаза 0 — страховка.** Зафиксировать поведение: набор скриншотов `Shot.gd` (несколько
  состояний — борд/мулиган/scry/picker/game-over) как визуальная регрессия; короткий чек-лист
  ручного смок-теста (драг-играть, атака, в ману, awaken, end-turn). Критерий каждой фазы — эти
  скриншоты/смок без изменений.
- **Фаза 1 — `CardData` (чистый модуль).** Перенести ~20 view/rules-функций, которым нужен лишь
  `cards` + переданный пул: `_def/_display_id/_name_of/_text_of/_needs_target/_target_side/
  _is_creature/_has_keyword/_keyword_n/_total_cost/_can_afford/_can_afford_with_shift`. Сделать их
  **чистыми** (принимают данные параметрами, не читают глобалы). Это первый тестируемый шов →
  добавить первые GDScript-тесты (GUT или простой `assert`-раннер).
- **Фаза 2 — `Tokens`/`Theme` + фабрики.** Единая таблица токенов (палитра/типошкала/радиусы/
  тени/размеры карты). Свести дубли: один `gem(text, ring, size)` (убить `_gem`/`_stat_gem`),
  один `art_node(card_id, px_or_full)` (убить `_art_thumb`/`_art_full`), один набор стиль-фабрик
  (поглотить `_round_style` и инлайновые StyleBox). Заменить 65 инлайновых `mouse_filter` хелпером.
- **Фаза 3 — виджеты в `class_name`-модули.** По одному классу за раз (каждый — отдельный коммит):
  `CardView`, `HeroMedallion`, `PilesColumn`, `ManaRow`/`AwakenChip`, `BoardRow`, `HandRow`,
  overlays (`MulliganPanel`/`ScryPanel`/`GameOverPanel`), `ColorPicker`. Каждый принимает данные,
  emit-ит сигналы-намерения; `Main` подключает сигналы к `_send`.
- **Фаза 4 — сервисы `Net` и `GameState`.** Вынести WebSocket (`_on_connect/_process/_send`,
  recv-парсинг) в `Net`; диффинг и хранение view (`_ingest_view`, `_prev_hp`, summon/death-детект)
  в `GameState`. `Main` подписывается на их сигналы.
- **Фаза 5 — `Fx`/`Animator`.** Собрать lunge/shake/pop-in/flash/float-numbers/motes в один
  модуль поверх `FxLayer`. `Main` после этого — тонкий координатор.

После фаз 1–5 `Main.gd` ужимается до склейки модулей.

## 5. Отдельно (НЕ в рамках модуляризации, своим проектом)

- **Инкрементальный апдейт борда** вместо полного `_rebuild` (diff-патчинг узлов). Делать ТОЛЬКО
  после модуляризации (когда есть `BoardView` с явной моделью узлов). Даст дешевле перерисовку и
  чистые межсостоянные анимации (карта рука→стол).
- **Типизированная модель** (`CardDef`/`Creature` обёртки вместо `Dictionary`) — убирает
  primitive-obsession. Большой заход; делать после того, как структура разнесена.

## 6. Правила безопасности рефакторинга

- **Только чистые переносы** на фазах 1–4: поведение байт-в-байт, проверка по `Shot.gd`-скриншотам
  и смок-чек-листу. Никаких «заодно поправлю фичу».
- Один модуль = один коммit (English, без подписи); не коммитим, пока пользователь не проверит.
- Парс-чек после каждого шага: `Godot --headless --editor --quit-after 2` (ноль SCRIPT ERROR).
- Числа/поведение не «улучшаем» по дороге — это отдельные задачи в BACKLOG.

## 7. Порядок и оценка

Рекомендованный порядок = фазы 0→5 (снизу вверх). Самые дешёвые победы и наибольший анти-дубль —
**Фаза 1 (CardData) и Фаза 2 (Tokens/фабрики)**; с них и начинать. Фаза 3 — самая объёмная
(разбита по одному виджету). Фазы 4–5 — небольшие. Инкрементальный апдейт и типизация — потом.

## 8. Инкрементальный апдейт борда — план реализации (АКТИВНО)

**Проблема.** Сейчас каждый `view` = полный `_rebuild` (снос `root_box` → пересборка). Узлы существ
создаются заново → нельзя анимировать переход живого узла (рефлоу при сдвиге, «карта летит
рука→стол»); `pop_in`/`lunge`/`flash` работают только потому, что между двумя view нет ре-лэйаута.

**Решение.** Существа на борде — **постоянные узлы, ключ = id существа**, в **слое с ручной
раскладкой** (не `HBoxContainer`), реконсилируемые на каждый view. Позиция тогда твинится.

**Модуль `BoardLayer` (`board_layer.gd`, `class_name BoardLayer extends Control`).** По одному на
сторону. Владеет `_nodes: {cid: UiCard}`. API: `sync(board: Array, ctx: Dictionary)`, где `ctx` —
колбэки/флаги от Main (build_card, can_attack, drop-хендлеры, my_turn …). Делает:
- считает целевые позиции слотов (портируем overlap-математику из `_board_row`);
- для каждого существа: взять-или-создать узел, **обновить данные+визуал**, поставить/твинить на слот;
- новое существо: создать в точке входа (из руки/`pop_in`), въезд-твин;
- ушедшее (id пропал): анимировать смерть, освободить;
- переупорядочивание = ретаргет позиций (твин).

**Узел существа.** Текущие замыкания (`can_drop_fn`/`drop_fn`/`payload`) **захватывают `cr`** —
при переиспользовании узла данные устарели. Чиним: хранить текущий `cr` в `node.set_meta("cr", …)`,
замыкания читают `get_meta("cr")`. Обновление узла = обновить мету + перерисовать гемы/статусы/
modulate/ability-dock (контент лица можно пересобирать, **сохраняя внешний узел** — дёшево при ≤8
картах, а выигрыш в стабильности identity для твинов).

**Фазы (каждая — парс+скрин-парити, затем live-проверка пользователем, отдельный коммит):**
- **P1 — паритет. [СДЕЛАНО]** Борд → `BoardLayer` (`board_layer.gd`, по одному на сторону) с ручной
  раскладкой и реконсиляцией; постоянные узлы по `cid` спасаются перед сносом и реатачатся в свежую
  половину. Замыкания карты читают `node.set_meta("cr")` вместо захвата `cr`; узел переиспользуется,
  контент перерисовывается на том же внешнем узле (`_creature_card` = make, `_refresh_creature` =
  update). lunge/death/gap/anim переведены на `_creature_node`/`_take_creature`. Позиции —
  мгновенно. Проверено: статик-паритет, реконсиляция через 2 view, смерть играет в слоте (фикс:
  `take()` не отвязывает узел до чтения позиции). Live-проверка взаимодействий — за пользователем.
- **P2 — движение. [СДЕЛАНО]** `BoardLayer._layout(animate, instant)` твинит позицию существ
  (плавный рефлоу: соседи скользят при смерти/вставке), `_place` киллит старый твин при ретаргете.
  Свежесозданные узлы ставятся мгновенно (их вход анимируется отдельно). Дырка при драге
  открывается/закрывается плавно; ресайз окна — мгновенно; no-op view не дёргает борд (порог 0.5px).
  Въезд карты: `_play_at_drop` запоминает точку дропа (`_pending_summon`), `_animate_changes` зовёт
  `Fx.fly_in(node, from_global)` для своего призванного существа (враг/токены — `pop_in`), затем
  чистит pending. Проверено: рефлоу (узел 656→565 плавно), no-op (без дрожи), fly-in (старт у точки
  дропа → слот). Live-проверка — за пользователем.
- **P3 — рука. [СДЕЛАНО]** `HandRow` (`hand_row.gd`): постоянный веер руки, реатачится каждый
  ребилд. У карт руки нет стабильных id (view даёт `hand` = список card_id, возможны дубли) →
  жадный матч новых карт к узлам по card_id: выживший слайдит на новый слот, добранная карта —
  свежий узел, сыгранная — освобождается. Переиспользуемый узел всегда тот же card_id → лицо не
  меняется, обновляются только index/playable (через `node.set_meta("hand_index")`, дабл-клик
  читает мету — без переподключения сигнала). `_layout` твинит позиции и держит draw-order = порядок
  руки (правая карта поверх левой). Проверено: статик-паритет; реконсиляция (узлы переиспользуются,
  сыгранная карта удаляется, сосед слайдит 734→642). Live-проверка — за пользователем.
- **P4 — мана-ряд/стопки. [СДЕЛАНО]** Дёшево, в рамках ребилд-модели (без персистентных узлов):
  `_animate_piles` диффит твои `deckCount`/`graveyardCount`/сумму `crystals` (prev vs новый view) и
  пульсит соответствующий chrome-узел через `Fx.pulse` (scale-отскок + бриф-яркость, scale —
  визуальный трансформ, колонку не дёргает). Узлы (`_mana_block_node`/`_deck_pile_node`/
  `_grave_pile_node`) захватываются в `_piles_column` для своей стороны. Триггеры: +кристалл (банк/
  рамп) → мана-блок; колода уменьшилась (добор) → стопка колоды; +в сброс (смерть/заклинание) →
  стопка сброса. Проверено: все три пульса срабатывают на изменении, prev обновляется.

**Безопасность.** P1 — строгий паритет (никаких новых анимаций), проверка скриншотом против
текущего `_shot.png`. Не коммитим, пока пользователь не проверит вживую. Числа/правила не трогаем.
